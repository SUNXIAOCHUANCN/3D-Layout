# P3：验收未通过也保留结果

## 1. 首版明确策略

本轮用户已同意：正常执行后任务验收不通过，也保留修改，由用户决定是否撤销。

| 结果 | 首版处置 |
| --- | --- |
| 正常执行、全部通过 | 提交编辑事务、保存，显示完成 |
| 正常执行、判据 fail/uncertain、修复用完、任务跳过 | 提交编辑事务、保存，显示保留且存在问题 |
| 正常执行但无实际修改 | 无修改，不生成虚假的撤销入口 |
| 澄清/不支持/计划无效，未开始修改 | 无修改，显示原因，不谎称撤销了内容 |
| 真实执行异常、事务/场景上下文失效 | 保留现有恢复路径，必要时回滚或 error_locked |
| 用户取消、模块卸载 | 首版保留当前取消并撤销语义，按钮明确写明；停止并保留作为单独扩展 |

模型超时后的部分结果保留可后续实现，但不得在首版用一条 `else commit` 把所有异常都提交。普通判据失败必须与基础设施错误结构化区分，不靠错误文本包含 finalCheck 判断。

## 2. 工作流结果与处置分开

建议在 RunOutcome 增加 `retained_with_issues`，共享 completed 的完整报告字段：summary、plan、regions、finalCheck，并附 issues。该名称表示正常结果保留的意图；实际是否已提交由 controller 的处置回执确认。

更彻底拆分可使用 WorkflowResult 与 RunOutcome 两层，但首版不要求全量重构。关键是不在 mainGraph 把普通 finalCheck 未通过直接编码成 write_failed/rolled_back。

finalCheck 返回结构化未通过项：taskId、criterion/constraint、fail/uncertain、原因、证据。读取失败、写入不可信等基础设施问题单独记录 failureCategory。

任务与区域状态仍按实际报告 fail，不能因为保留而改成 pass。finishFail 不能丢弃本区之前通过任务，未执行任务需显式 skipped 并注明 dependency_failed 或 region_stopped。

## 3. 控制器终态处理

建议流程：

```text
停止新增作业、确认工作流已收敛
→ 拒绝迟到写入
→ 等 sceneIdle
→ 核对场景/token仍有效
→ 对 completed/retained_with_issues 提交事务
→ 获取提交回执与历史标识
→ 设置已保留状态、释放执行锁
→ 保存场景
→ 记录保存结果
→ 清理 token、幂等、run 临时状态
```

不要无限保留 open transaction 等待用户点击接受。提交事务是形成可撤销历史，不代表验收通过。

commit 应返回是否有修改、sceneId、historyTransactionId 等回执。当前 writeFacade 的 commitRun 是 void，adapter 的 commitTargetTx 直接返回 true，底层 handle.commit 也可能静默 no-op；接入结果回执时须验证真正提交，不能凭调用成功就宣称持久历史存在。

保存失败不撤销已提交修改，显示“已保留但保存失败”，允许重试。无写入时不把上一条用户历史误认成本轮事务。

提交和失败路径都应可靠 endRun 清理；迟到模型回调不能在终态写入。controller 错误时日志应记录实际处置，而不只是工作流原先期望的 kind。

## 4. 用户撤销 API

运行级历史关联建议：

```ts
type RunHistoryRef = {
  runId: string
  sceneId: string
  sceneSessionId: string
  transactionId: number
}
```

sceneSessionId 区分同一 sceneId 的重新加载，防止事务计数重用。通过 adapter 暴露窄接口，例如 queryRunUndoEligibility/ref、undoRun/ref；UI 不直接 import core/edit 绕过模块。

撤销检查：

1. 无活跃 Agent run，编辑器不被其他写者占用。
2. 当前场景及会话匹配。
3. 该事务仍在历史中，且未被撤销。
4. 若它是栈顶，调用编辑历史撤销并验证结果。
5. 若其后有编辑，拒绝“仅撤销本轮”的快捷操作，返回后续历史数量，提供历史查看入口。

首版不做选择性撤销，也不自动 undoTo。若另行提供“回到本轮之前”，必须明确会撤销本轮和所有后续编辑，并获得该具体操作的用户确认；默认界面只保留安全的栈顶撤销。

撤销后刷新实时场景、结果状态与分区归属。成功后可沿用自动保存策略保存撤销结果；失败则明确标示保存失败。已有编辑器 redo 可以保留，但若 redo 后刷新结果卡片，必须依据历史和当前状态更新，不让按钮仍声称已经撤销。

历史通常只在当前编辑会话存在。首版跨刷新恢复分区，不承诺跨刷新仍能撤销旧 run。

## 5. UI 和事件投影

增加“改动已保留，存在未通过项”的终态，不能纳入 active/busy 阶段。同步修改 CoAgentPhase、uiProjection、uiStore、useCoAgentModule、hostLocks、进度、图页终态和日志。

结果卡片展示：

- 执行：完成/部分完成；
- 验收：通过/未通过/无法确认，按任务列出；
- 修改：保留/撤销/无修改；
- 保存：server/download/失败；download 不等同服务器落盘；
- 实际新增/调整/删除数量，来自任务记录，不用 executor 自述。

按钮首版：查看问题、查看历史、可用时撤销本轮、保存失败时重试。

“继续修复”若实现，必须以新 run 的当前场景重新读取和授权，携带旧问题作为上下文，而不是恢复旧 token 或机械重放旧 add 计划。数量目标应表示尚需完成的工作，原对象作为明确目标，避免跨 run 再次重复新增。此按钮可后置，不交付空按钮。

事件建议保留 `run.committed` 表示物理提交，payload 携带 validationStatus/historyRef；新增用户撤销事件。日志开头同时显示验收和处置，避免 `failed` 一个词掩盖“保留了还是撤销了”。

## 6. 必测行为

- 一个任务 fail，另一区域 pass：最终两区已有修改均保留，报告不冒充通过。
- 首次 repair fail 后正常结束：提交一次，历史一条，token失效。
- 完成后直接撤销：完整恢复新增/修改/删除对象，且不影响更早历史。
- 用户后续编辑：快捷撤销不误撤销用户最新动作。
- 无修改、场景切换、重新加载、历史清空：按钮准确不可用。
- commit无效/rollback失败/保存失败：三者被区分，状态与真实场景一致。
- 原取消和卸载测试继续通过；普通验收失败测试改为保留语义，并保留异常回滚测试。
