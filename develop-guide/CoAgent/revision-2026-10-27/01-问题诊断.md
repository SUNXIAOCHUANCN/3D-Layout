# 现有问题：为什么一次简单加房屋任务没有留下结果

## 1. 实际发生了什么

样本日志：[coagent-20261026-154629-run-mvoydj9p-1.md](../../../logs/coAgent/coagent-20261026-154629-run-mvoydj9p-1.md)。

用户请求是“在中央白色雪原添加几栋房屋”。运行从 2026-10-26 15:46:29 到 15:51:07，耗时约 279 秒。模型请求有回复，编辑工具也成功添加了房屋；最后没有留下结果，是因为验收失败后系统撤销了整轮修改，并非一次网络调用直接失败。

过程如下：

1. 规划器把任务分成西侧新增两栋、东侧新增两栋，后者依赖前者。
2. 首轮在 `[-18,1.6,-68]` 和 `[-18,1.6,-82]` 添加房屋。两栋与雪山体相交。
3. 执行器自己的首次检查没有包含关键山体，未及时纠正落点。
4. 判定器看不清新增房屋；碰撞验收也失败。
5. 修复轮没有移动原来的房屋，而是在其他位置又添加两栋。原来的两栋继续存在。
6. 最终场景从 32 个对象变成 36 个，但任务仍未通过。东侧任务没有执行。
7. 一次修复用完后，终检失败，整轮回滚。

## 2. 主要问题及证据

| 问题 | 证据 | 实际影响 |
| --- | --- | --- |
| 原场景碰撞被算进新任务 | 日志事件 96；海水与船、地形与街道也进入失败列表 | 新房屋即使摆对，也可能过不了 |
| 修复变成再次新增 | 事件 60/61 首次新增，118/119 再次新增不同 ID | 两栋变四栋，旧问题仍存在 |
| 查询返回过期成员 | 事件 108、136 的 `scene.list_region` 仍返回 32 个 | 模型无法正确判断自己已经做了什么 |
| 数量验收口径错误 | 最终 task-2 未执行，其区域总数指标却满足 36 | 别的任务重复新增也能替它“达标” |
| 图片无法支持细节判断 | 两次判定均表示不能清晰辨认新增房屋 | 模型无法可靠复查自己的操作 |
| 截图更新有上限缺陷 | 执行器只附前两张截图 | 后续拍到的新图不一定进入模型上下文 |
| 判定引用错误 | 首次 judge 引用不在证据集合中的 `…-1` | 判定被标为不可信，但不是唯一失败原因 |
| 任何验收失败都可能抹掉本轮成果 | 终检返回 `rolled_back` | 用户无法看到和保留部分有价值的结果 |

注意：561 对、630 对是检查的对象配对数量，不是碰撞数量。它们分别对应 34、36 个对象的全量两两组合。

## 3. 代码为何会出现这些行为

- `rendering/geometry.ts` 把动态对象与静态对象合并后全量配对，包含静态与静态的旧碰撞。
- `tools/sceneTools.ts` 的区域摘要直接读取冻结的 `region.objectIds`；`services/validation.ts` 又通过当前坐标筛选对象，查询与验收不是一个口径。
- `workflow/regionGraph.ts` 累积了写集，但修复调用执行器时未显式提供累计创建对象和当前状态；传入的可写列表也是运行开始时的集合。
- `agents/executor.ts` 修复建立新对话，只带原任务和文字反馈。原任务仍写“新增两栋”，状态却没说明两栋已经存在。
- `regionGraph.ts` 切下一任务时未明确清空写集和执行证据，存在任务间串记录风险。这是源码发现的潜在问题，不是本样本中已发生的第二任务行为。
- `tools/cameraTools.ts` 捕获固定 320×240；区域总览不适合确认房屋朝向和接地。
- 自动验收标注采用“目标、原有对象、新增对象”后截前 12 个；本例新增对象排不到前 12 个。标注遗漏不等于对象没有被渲染，但使辨认更困难。
- `agents/judge.ts` 主要加载固定 before/after 图片，额外证据 ID 不代表额外图片已送达。
- `mainGraph.ts` 将终检失败映射为回滚结果；`runController.ts` 随后执行真正回滚。

上述视觉结论来自日志与代码，未通过本次文档工作直接重看原始截图。

## 4. 为什么不应简单取消所有检测

树冠交叠、草丛穿插、石块嵌入地形可以是正常效果。把“网格相交”直接解释为“布局错误”不合理。因此碰撞应默认是诊断信息；明确要求零碰撞时才是硬性判据。

但是，取消碰撞不会修好过期状态、重复新增和截图反馈问题。即使没有碰撞验收，这些问题仍会导致数量不对、误操作或模型自报完成却与实际不一致。

用户已报告碰撞策略改动完成，后续实施应保留其用户原文依据规则，同时检查底层配对范围是否仍待修复。

## 5. 分区为什么也需要长期保存

当前分区主要存在 runtime 内存。刷新或重新打开后，可能需要再次调用模型划区，区域 ID、边界和人工修正难以稳定延续。

长期保存的应是区域定义和经过核对的对象归属，不是永远不更新的对象列表。场景新增、删除或撤销后，恢复的分区仍需与当前场景对账。
