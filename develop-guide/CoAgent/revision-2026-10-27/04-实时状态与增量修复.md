# P1：实时状态与增量修复实施方案

## 1. 目标与不变量

目标是任何时刻查询、executor、judge 和 finalCheck 对当前对象与任务成果有相同理解；修复不会重复创建完整目标数量。

必须满足：

- 每次读取使用一个编辑器快照，返回 sceneRevision；同一响应的数量与列表来自同一快照。
- 一个现存对象只有一个主区域归属，或明确处于全局只读/未解决状态。
- 一个 run 内创建的对象保留 creatorTaskId，不因换任务而归另一个任务。
- 成功写入即时登记；失败不登记；重复成功回执只登记一次。
- 数量名额基于本任务仍存在的新增对象，不是调用次数、区域总量或总创建历史。
- 任务开始基线不变，修复修改依据持续刷新。

## 2. 建议新增状态服务

建议 `runtime/runState.ts` 定义 run 级服务，生命周期由 runController 拥有，通过 WorkflowContext 提供窄接口。服务内按 taskId 分组，regionGraph 不再拥有第二份权威写集。

示意数据结构（以最终合约命名为准）：

```ts
type ObjectOwner = {
  regionId: string | null
  creatorTaskId: string | null
  source: 'initial' | 'manual' | 'agent'
  readonly: boolean
}

type TaskLedger = {
  taskId: string
  regionId: string
  phase: 'initial' | 'repair'
  attempt: number
  createdIds: Set<string>
  modifiedIds: Set<string>
  removedIds: Set<string>
  appliedReceiptKeys: Set<string>
}
```

`liveCreatedIds`、当前属性、当前指纹从 ledger 与快照计算。不要把 Set 直接作为 LangGraph 或 JSON 返回值，边界上转换为可序列化 DTO。

建议服务方法：

- `registerTasks(plan)`：规划校验成功后注册任务、数量和权限规则。
- `resolveRegion(snapshot, regionId)`：返回当前成员和权限分类。
- `getTaskSnapshot(snapshot, taskId)`：返回实时任务成果、数量、当前变换。
- `validateWrite(taskId, command, snapshot)`：检查任务授权和数量。
- `recordReceipt(callKey, receipt)`：登记已确认写入。
- `finish()/dispose()`：禁止迟到写入并释放 run 临时记录。

规划器尚未生成任务时，查询可以从冻结初始归属与实时快照解析；不要要求读取工具必须有 taskId。

## 3. 区域成员口径

优先把归属解析抽到共享纯函数，供持久化恢复和运行状态使用：

```text
regionMembers = (初始归属该区的 ID ∪ 本轮在该区创建的 ID) ∩ 当前存在的 ID
writableMembers = regionMembers - readonly - unresolved
taskWritableMembers = writableMembers ∩ 当前任务允许对象
```

区域 objectIds 不重复包含全局只读背景。若旧数据已有交叉，进入运行前规范化并记录变化；`readonlyObjectIds` 单独返回。`objectCount` 与返回的 objectIds 长度一致，`region.object_count` 使用同一个主成员集合。不要再一处按位置筛选、一处按冻结列表计数。

位置校验独立处理：对象出界不会偷偷更改所属区域。运行内跨区编辑仍拒绝。运行外的手动移动在下一轮或分区恢复时核对，存在冲突则标记，不自动放开权限。

修改 `tools/sceneTools.ts` 返回 sceneRevision，区域与任务计数分清。`services/validation.ts` 改为接收统一解析结果或 resolver，不能通过全场坐标另算一套。

## 4. 写入原子路径

当前 `runController.context.applyWrite` 已通过 scheduler.runScene 调用 applyAuthorized，应在这个入口集中整合，而不是仅在 edit.add handler 加检查。

推荐顺序：

```text
入队
→ 在队列内部再次检查 abort、run/scene 身份和 token
→ 判断是否命中同一幂等调用的既有回执
→ 获取当前快照
→ 检查任务操作、对象归属、只读、数量与边界
→ 执行现有 applyAuthorized（保留指纹与底层幂等）
→ 成功后登记任务 ledger、run 可写集合和最新回执
→ 返回结果
```

关键细节：

1. 旧逻辑只在入队前检查 abort 不足以防止排队期间取消。队列内也检查。
2. 名额检查不得在已成功的幂等重放之前拦截，否则“新增成功但响应丢失”重试会错误得到超额。
3. 可以给写门面提供成功执行后同步登记钩子，或在同一 runScene 闭包内处理；不得出现写成功而正常响应先于登记。
4. 同一个 `(runId, taskId, toolCallId)` 参数不同继续报 invalid_arguments，不覆盖旧回执。
5. 若登记出现不可恢复异常而底层已写成功，按基础设施异常处理，不能向模型返回“完全没改”。
6. 从 registry 的 createdByRegion 迁移到共享归属服务，避免多份集合渐渐分叉。
7. 底层权限检查保留；任务级规则是额外收紧，不替代 run token 和指纹。

## 5. 结构化数量与权限

UnitTask 建议增加：

```ts
creationTarget?: { minCount: number; maxCount: number }
```

新 add 计划必须存在、整数非负、min≤max，并受合理任务规模上限约束。精确两栋填写 2/2；“几栋”由规划器选择并写入 assumptions。非 add 任务不得用这个字段隐式获得新增权限。

禁止从 `region.object_count >= N` 或 objective 正则推导目标，旧计划需重新规划或明确迁移。

权限矩阵：

| 对象/操作 | 允许条件 |
| --- | --- |
| 新增 | task 声明 add，且存活新增数小于上限 |
| 调整/删除本任务新增对象 | 同区、对象现存、有效指纹；视为完成 add 任务的内部修复能力 |
| 修改原场景对象 | 在 targetObjectIds，且 allowedOperations 声明对应操作 |
| 修改其他任务新增对象 | 仅当当前任务获得显式且经过计划校验的授权；首版无动态引用则拒绝 |
| 全局只读、邻区、无归属对象 | 拒绝写入 |

达到上限时返回稳定错误码（例如 `task_creation_limit`），附 current/max、liveCreatedIds 和“调整现有对象或先删除替换”的建议；同步更新 ToolError 合约及模型描述。

删除本任务新增对象释放一个名额；对对象身份去重，不能把重复删除当作继续释放名额。modified 与 removed 分开记录，删除对象不进入后续需要现存对象的几何或截图查询。

## 6. 修复上下文

`ExecutorInput` 增加 `executionState`，由程序在每轮开始从同一新快照生成：

```text
phase、attempt、sceneRevision
目标数量、存活新增数、remainingAddCapacity
本任务创建/修改的当前对象（ID/ref/transform/fingerprint）
已删除对象摘要
当前任务允许操作对象
taskBeforeObservationId（只作比较基线）
latestObservationId
未通过/不确定的判据及具体问题
```

修复提示明确“上一轮修改仍保留”。把 feedback 作为问题说明，而不是唯一状态传递通道。可继续使用新对话，不需要把全部旧工具 transcript 塞回去。

最新指纹可作为 expectedFingerprint，之后如果过期仍由现有写门面拒绝。任务开始时的旧基线指纹不得被标为“当前可直接用”。新增对象不在原基线里，不能强制要求用原 baseline 作为它的修改依据。

目标对象数据过大时只截取展示，不截取权威 ledger；明确 truncated、提供分页查询。新增上限让普通任务天然保持小规模。

## 7. regionGraph 生命周期

- prepare：创建该 task 的基线、初始化观察状态，禁止带入上一任务写集。
- execute：读 task snapshot → runExecutor → 从共享状态读取成果，不再仅靠 toolResults 反推权威状态。
- judge：使用存活目标/新增/修改对象；标注优先这些对象，再补环境。
- repair：更新 phase、attempt 和问题；保留同一任务 ledger 与原始基线，刷新当前状态。
- advance：清空本任务临时反馈、执行证据指针和工作轮次；运行级归属不清空。
- finishFail：保留此前已完成任务结果，加上失败任务及未执行任务，不能只返回 `[failed]` 丢掉历史结果。
- 下一轮 run：从当前场景与分区初始化，不继承上轮活跃 token/临时任务权限。

TaskResult 区分累计创建历史与存活成果。可以增加 liveCreatedObjectIds、removedObjectIds，保留 createdObjectIds 的审计语义；所有消费者应明确使用哪一项，不能偷偷改变一个旧字段含义而漏掉 finalCheck。

## 8. 验收和日志

增加程序生成的 `task-created-count:<id>` 检查，采用任务存活新增数。模型不能推翻这个检查。所有原有视觉判据仍保留。

记录 `task.state`（attempt、revision、存活数量）、`write.rejected`（规则及对象 ID）、`repair.start`（当前成果及问题），禁止只记录自然语言自述完成。

数量检查不证明资产类别正确：实际创建的 ref/类型仍应与计划要求核对，现有视觉或新增结构化模型限制可以负责。首版至少将 ref 暴露给判定，不能声称“数量正确即房屋正确”。

## 9. 完成标准

同一个任务创建两栋后，修复上下文能看到两栋；第三次 add 被拦截；原对象移动成功；删除一栋再创建可行；同区第二任务查询包含前一任务成果，但自己的新增数为零。全链路数量和日志一致，旧碰撞依据测试继续通过。
