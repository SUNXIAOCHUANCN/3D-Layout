## 2. 先开工，不把环境选择当成架构阻塞

对应问题：#1、#2、#3、#4、#5、#51、#52。

### 2.1 Git 与测试

- Git 是推荐的协作保障，不是代码运行和测试的前提。未得到用户明确授权，不自动 `git init`、提交或重组仓库。
- 没有 Git 时，先串行开发，建立改动清单并保留所改文件的可恢复副本；不要让多个 SubAgent 同时修改公共文件。
- 建议使用 Vitest。配置放 `src/modules/coagent/vitest.config.ts`，通过显式 `--config` 调用；不默认修改宿主 `vite.config.ts`，也不要求在 src 根新增配置。
- `package.json` 和 pnpm 锁文件仍属于原规格允许的必要改动。依赖版本需根据真实安装与构建结果锁定。

### 2.2 LangGraph 失败时怎么办

LangGraph 仍是首选。W02 若失败，先定位到浏览器运行时、依赖版本或 API 使用问题，提供最小复现。

不能一失败就静默改成另一套架构。可以用 fake WorkflowRunner 解锁其它模块开发；正式改为手写工作流需报告原因并获得用户确认。接口隔离的目的就是让这个决定不影响相机、工具和事务。

### 2.3 第一阶段范围与验收

建议以 **W00～W05 为第一个交付门**，不是将最终目标缩小为假模型演示。通过后继续 W06～W09，真实 API 不应阻塞前半程。

浏览器检查优先自动化：截图、像素采样、相机矩阵前后比较、renderer 状态检查、交互测试。主观视觉效果和研究演示由用户验收，但开发者不能把所有 GPU 检查都交给用户手测。

若开发环境确实没有浏览器自动化能力，提交复现步骤与未验证清单，不把这些检查写成已通过。

## 3. 复用与互斥的边界

对应问题：#6～#13。

### 3.1 复用什么

允许通过 modelAdapter 或模块配置适配层复用现有 LLM 设置和凭据，避免用户重复配置。运行开始时冻结配置；不得接入旧 Agent 的任务生命周期。

纯函数可复用，但必须没有旧 session/store、全局写入等副作用。若原文件一导入就带入旧插件运行逻辑，不直接复用；可以在 modules 范围内提取小型共享函数并做等价测试。

CoAgent 自己维护结构化事件与证据日志，不直接以旧 markdown recorder 作为事实记录源。需要 markdown 摘要时，从 CoAgent 日志派生。

不接入旧 WebSocket/loopback 任务调度系统。模型网络层可复用现有已配置通路，不把“必须直接连供应商且禁止现有代理”设为额外限制。

### 3.2 UI 可共存，写入必须互斥

两个面板可以同时显示，但同一时间只能有一个 Agent 执行。谁已在运行，另一个就不能开始；不自动中断对方，也不自动排队。

第一版保持 core 零修改。仅在 commands 分发点加判断也挡不住直接调用 edit 的路径，不能据此声称获得真正的统一写锁。

优先 App 接线和入口禁用。若历史模块无法通过宿主可靠禁用，允许在 `modules/history` 增加最小 disabled 接口。这符合原规格“其它 modules 的最小互斥接入”。

执行期间：

- 禁止切换场景、undo/redo、导入、手动变换和旧 Agent 执行。
- 允许用户旋转/缩放视口。
- 默认禁用对象点选，避免与编辑交互混淆；程序内部读取对象不受影响。
- 关闭 CoAgent 直接执行取消、等待清理、再卸载，不额外弹确认。

若无法覆盖已知正常入口，W03 不通过，必须列出具体绕过路径；不能用“core 不改”作为放任抢写的理由。

## 4. 模型协议：先解决证据传递，不先押供应商

对应问题：#14～#20、#31。

### 4.1 图像传递

复用旧客户端时，采用合法工具调用结果附图。**但“读取已有证据”和“重新拍照”必须分开。**

补充只读工具 `observation.get`：

- 输入：当前 run 允许访问的 observationIds。
- 输出：已保存的实际图像及相机、ID 映射等摘要。
- 不重新渲染，不改变证据，不返回尚未解析的 objectURL 代替图片。

judgeAfter 通过该工具读取 baseline/before，再通过 camera.capture 取得 after。不能为了满足协议重新拍一张“before”：场景已经修改，重拍不是历史证据。

用户视口用显式捕获来源 `source: "user_viewport"`，区域相机用 `source: "region_camera"`；由 RenderPort 内部取得相机快照。用户视口只读，不允许 camera.set/focus 修改它。不需要在业务模块直接导入 engine。

### 4.2 结构化输出与依赖

默认使用 Zod 做运行时校验，并验证与已安装 LangGraph 版本兼容。

Plan/Verdict 默认通过终态工具 `submit_plan` / `submit_verdict` 提交；只有 schema 与业务校验通过才终止循环。不能假定所有供应商支持强制 tool_choice。

JSON 文本解析修复只作为供应商适配的显式后备路径，不在同一流程中随意接受任意格式。输出修复最多一次。

### 4.3 供应商、超时和并发

不根据品牌名称承诺能力。W06 选择用户已有凭据对应的具体模型，实测多图、工具调用和取消；未提供凭据时使用 fake，不宣称真实链路已完成。

全局并发 2，跨角色共享；使用公平等待队列，不为 judge 预留一路。执行/判定是阶段顺序，不能持有 semaphore 再等待另一个需要 semaphore 的模型调用。

超时返回 model_timeout，用户取消返回 cancelled；保留原始原因。MVP 不自动重试模型请求或场景写入。

输出 token 上限和图片尺寸由 modelAdapter/config 管理。图片在提交模型前降采样，原始证据保留；所有限制记录到日志。不将“支持全部推理模型”列为 MVP 门槛。

## 5. 场景、分区与遮挡：必须限制第一版承诺

对应问题：#21～#29。

清单中的场景对象数、跨度和资产尺寸来自提交的问题，本次未重新测量。开发者需在 W00 记录实际世界 bounds，不能把表中数字当成已验证常量。

### 5.1 两层验收场景

- 确定性测试场景：2～3 个区域、6～20 个简单对象，覆盖增改删、失败、取消与撤销。
- 研究演示场景：建议选 tri-biome 中经人工确认的村落工作区，首轮控制在 **不超过 3 个可编辑区域、50 个可编辑对象**；其它对象仍可作为只读背景和碰撞参照。

这是建议的演示范围，不是已证明的性能上限，也不意味着超过 50 个对象就无法运行。相机参数仍按实际 bounds 计算，不写死“200m”。

最终演示区域由用户确认即可，不应阻塞前面的确定性测试。

### 5.2 globalReadonly 与工作区

分区结果增加场景级配置：

```ts
type PartitionContext = {
  sceneId: string;
  partitionVersion: number;
  workingBoundsXZ: [number, number, number, number];
  globalReadonlyIds: string[];
  regions: Region[];
};
```

大型地形/水面候选可按实际 footprint 排序辅助选择，但最终由用户确认。名称和尺寸只能给建议，不能自动授权或排除对象。

globalReadonly 既不是“不可见”，也不是“碰撞忽略”。这三个概念分别记录，不能用一个标签混在一起。

归属按 XZ 计算，鸟瞰坐标转换采用 Y=0 参考平面。该平面只是二维分区坐标基准，不是物体落地高度；不能把对象统一移到 Y=0。

W00 抽样检查导入模型局部 bounds 和变换原点；检查真正影响 XZ 归属的偏移。默认以渲染世界 bounds 的 XZ 中心作为归属锚点，缺失几何时标记待确认。不要用改写模型 transform 的方式偷偷“修复原点”。

### 5.3 标记密度与遮挡

默认三级观测：

1. 全局鸟瞰 RGB 用于语义分区，不强制标全部对象 ID。
2. 区域图按可读性标记对象；太密时局部聚焦或分页。
3. 执行图优先标任务目标和必要参照对象，附明确 label→objectId 映射。

第一版仍采用 RGB 上的二维标记叠加；ID 材质 pass 是另一种可选观测能力，不把“编号图”暗中升级成实例分割项目。无法可靠确定可见性的标签必须标 uncertain，不能凭投影点推断物体可见。

允许生成额外的“隐藏指定背景物体”的辅助图，但：

- 默认正常 RGB 保留，用来展示真实上下文。
- 隐藏名单经用户确认，在截图 metadata 中记录。
- 临时隐藏必须 finally 恢复，不修改场景文档。
- 辅助图不能代替真实渲染图证明“没有遮挡”或“视觉效果已达成”。

## 6. 写入安全：有两处不能按问题中的假设实现

对应问题：#33～#39、#50。

### 6.1 preserve_objects 必须在写入前拦截删除

问题 #36 的建议不采纳。保留对象 ID 在任务中已知，完全可以在执行 remove 之前检查。

- preserve_objects 表示对象必须继续存在：禁止删除，最终再检查。
- 如要求“位置、朝向等也不能变”，另定义 immutable_objects，拒绝相应变换。
- preserve_count 是终态数量条件，不等同于任何一个对象都不可删除。

不能明知违反约束还允许写入，再等 judge 救场。

### 6.2 新增成功分成文档写入与渲染就绪

addAsset 返回成功仅表示文档已写入。新增工具需等待该对象正常加载和可观测，红色占位不能当成正常资产成功。

超时/加载失败返回错误并终止本轮，走整轮 rollback；第一版不实现嵌套事务或“只回滚这次 add”的隐含机制。只等一个 asset:loaded 事件不足以证明成功，需结合实际对象状态检查。

其它默认值：

- 中间编辑状态可见，面板显示执行中；不做独立影子场景。
- 新 ID 使用 `ca-<runShortId>-<counter>` 并检查冲突。
- 模型工具只接收完整 transform，不增加 delta 版本。
- 初始基线任一失败，整轮在写入前终止并保留诊断；通常此时没有事务需要回滚。
- 撤销/重做后自动重算归属并更新版本；不自动覆盖用户手调相机，提供“重新适配相机”操作。
- 第一版分区只存在内存和导出记录，刷新后重新预处理，不隐含实现持久化。

## 7. 判定、预算和证据资源

对应问题：#30、#32、#40～#44。

### 7.1 首批数值指标

| 指标 | 定义 | 不应宣称 |
|---|---|---|
| object_count | 指定对象集合中当前存在的数量，整数精确比较 | 视觉上看起来的数量 |
| min_xz_aabb_gap | 指定对象对/集合中世界 AABB 的 XZ 投影矩形最小间距，米 | mesh 最近距离 |

第二项 AABB 从当前实际几何与世界变换取得，旋转后重新计算。投影重叠时距离为 0，它可能比真实物体间距更保守；碰撞仍由独立工具判断。数值比较容差建议 0.01m，并写进指标配置和日志。

“至少 8m”如果只是 planner 自行猜测，不自动成为用户已确认的硬约束。影响布局幅度的假设应通过澄清确认；记录为 criterion 后才按明确条件验收。

所有要求满足的 criteria 均需 pass：数值通过不能抵消视觉失败，视觉通过也不能抵消硬条件失败。uncertain 在预算耗尽后整轮失败回滚，不偷偷“提交并标不确定”。

### 7.2 工具与图片预算

- 30 次为每 task 跨 before/executor/after/修正共享的工具预算，不是每角色各 30 次。
- 取证、读取已有证据和失败调用也计数；程序内部校验不计模型工具次数。
- 每任务初始 before 最多 3 张，每次 after 最多 3 张；允许提前不足额结束，不自动拍满。
- planner/preprocess 另有独立有界预算，建议各 20 次工具调用；不能借全局角色绕过任务预算。
- 图片以 PNG Blob 保存，URL 仅预览；发送模型时按适配器需要转换，日志不堆积 dataURL。
- 建议初始证据 Blob 上限 128 MiB，总图数上限 64；这是工程默认值，不是实测性能结论。检查已分配 render target 和像素缓冲，不能只限制压缩图片大小。
- MVP 默认串行捕获，图像最长边 1024px；小标签不清楚时局部聚焦，不无限提高分辨率。

捕获超时初始沿用 15 秒并记录耗时。同步 GPU 操作不能被普通 JS 超时强行抢占，因此这个值不是硬实时保证；W04 实测后调整。不要猜测“840 个对象必定多少毫秒”。

## 8. 其它问题用默认值收口

对应问题：#45～#49。

| 问题 | 默认处理 |
|---|---|
| 导出形式 | 一个 ZIP，使用经构建验证的 JSZip，JSON + PNG；必要依赖记入 package/锁文件 |
| 是否写项目 logs | 不写；浏览器下载独立日志包，不复用 core 保存日志副作用 |
| internal_error | 加入错误码清单 |
| no-op | 返回 completed，reason=no_op；不开始编辑事务，不生成空历史 |
| 澄清关联 | 新 run 保存 parentRunId，带前次澄清摘要与用户回答；重新读取场景，不复用旧执行计划 |

这些都是可逆的实现选择，无须每一项再等用户答复。若实际依赖不兼容，报告证据后调整，而不是先改业务契约。

## 9. 真正需要用户参与的事项

只保留下面几项，而且按开发阶段询问，不一次集中追问：

1. **进入 W06 时：**使用哪个现有模型配置进行真实测试？通过平台设置提供凭据，不要求粘贴到文档或聊天。

## 10. 给开发 SubAgent 的执行指令

先按本补充修订自己实际使用的 contracts 与任务计划，再推进 W00～W05。本文给出的是架构建议及默认值，不代表已经通过测试。

不再将全部 52 题作为开工问卷。优先验证：

- 配置放模块内的测试方案能否工作；
- 所有已知场景写入口能否合作式互斥；
- baseline 历史证据能否通过合法模型协议回传；
- globalReadonly 与可编辑工作区是否明确；
- 假模型闭环的提交、失败和取消是否正确。

如出现阻塞，用“具体文件/接口 + 复现步骤 + 对当前工作包的影响 + 最小替代方案”报告，不以笼统的“需要确认架构”暂停全部开发。
