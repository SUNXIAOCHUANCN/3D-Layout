# Three.js 场景导入规范

日期：2026-10-18  
版本：草案 v2（显式契约、自动原生入库）  
适用对象：准备将模型或场景导入 3D-Layout-Agent 的用户、Three.js 应用开发者。

本文定义拟实现插件的输入契约，不表示当前软件已经提供这些入口。实现方案见 [ThreeJS 双向导入导出插件架构设计](./ThreeJS双向导入导出插件架构设计.md)。发生能力差异时，以实际插件版本公布的支持清单为准。

本文约束一期的确定性导入入口。二期可用大模型辅助来源方准备声明，但候选结果须经用户审核，再满足本文全部条件；辅助模块不改变导入器本身不使用大模型的约束。

部署边界以架构文档 v3 为准：采用独立插件服务/CLI，不修改宿主核心。索引继续调用现有生成脚本，安装期间要求单写入者，不并行运行索引脚本、修改目标目录或刷新宿主；插件锁不约束外部脚本，不承诺多目录发布的强原子可见性。成功后通过新标签页打开 `?scene=<scene-id>`。默认导出已保存的磁盘场景，未保存编辑需先通过原有保存功能保存。

## 1. 基本原则

**来源方负责声明资产边界、语义名称和资源关系；导入器按明确规则校验、转换、入库，不使用大模型识别、分组或命名。**

导入结果必须与现有工程格式一致：场景进入 `scenes/<scene-id>/`，模型进入全局 `assets/models/<model-id>/`，并更新两个索引。场景“自带模型”指提交的模型随场景一起入库，不指在场景目录中维护私有模型库。ZIP 只是可选传输容器。

模型既可以来自 GLB/glTF 文件，也可以由 BoxGeometry、CylinderGeometry 等基础形状组合生成。插件负责把输入转换为统一的静态模型与场景数据，不要求源项目提前采用 3D-Layout-Agent 的目录结构。

本文中“必须”表示导入所需条件；“建议”表示提升成功率的做法；“拟支持”表示计划能力，不能理解为已实现。

## 2. 输入方式

| 输入方式 | 需要提供的内容 | 计划定位 |
|---|---|---|
| `.layout.zip` 场景包 | 场景文档、模型、资源清单及依赖 | 首阶段完整场景交换入口 |
| `.model.zip` 模型包 | 模型文件、元数据及资源清单 | 首阶段单模型交换入口 |
| `.glb` | GLB 本体；若仍有外部资源引用，也必须提供依赖 | 外部模型接入阶段 |
| `.gltf` 文件集合 | glTF、引用的 buffer、纹理等，保留相对目录 | 外部模型接入阶段 |
| Three.js 运行时场景 | 源应用通过配套 SDK 导出场景快照 | 外部场景接入阶段 |
| Three.js Object JSON | 对应对象数据和完整资源集合 | 后续兼容入口，限定对象类型及版本 |

任意命名为 `scene.json` 的文件不一定是受支持格式。第三方自定义 JSON 需要提供格式适配器，不能仅靠文件扩展名识别内容。

**JavaScript/TypeScript 源码、HTML 页面和网页地址不作为直接执行的导入文件。** 对于代码生成的场景，应在可信的源应用中运行完成，再通过 SDK 导出实际对象和资源。

首版目标是创建并打开原生新场景，以及模型入库；合并当前场景作为后续能力。所有输入都必须提供下面的导入声明。只有一个 GLB 而没有资产名称和实例声明，不满足自动导入要求。

### 2.1 必需的导入声明

文件交付时提供 `layout-import.json`；SDK 导出时提供等价配置，并将其写入交付目录。该文件独立于原生 `scene.json`，不改变现有数据契约。

```json
{
  "format": "3d-layout-import",
  "schemaVersion": 1,
  "scene": { "id": "demo-forest", "name": "示例森林" },
  "coordinates": { "metersPerUnit": 1, "up": "+Y", "handedness": "right" },
  "models": [
    {
      "key": "pine-tree",
      "name": "松树",
      "category": "vegetation",
      "tags": ["tree", "forest"],
      "source": { "file": "resources/pine.glb", "root": "whole-file" }
    }
  ],
  "instances": [
    {
      "id": "pine-001",
      "modelKey": "pine-tree",
      "name": "入口松树",
      "transform": {
        "position": [2, 0, 3],
        "rotation": [0, 45, 0],
        "scale": [1, 1, 1]
      },
      "visible": true
    }
  ],
  "environment": { "background": "#1c2128", "sunIntensity": 1.6 },
  "cameras": [
    { "id": "main", "position": [8, 6, 10], "target": [0, 0, 0], "fov": 50 }
  ]
}
```

字段规则：

- `scene.id`、模型 `key`、实例 `id` 必填，使用小写 ASCII 字母、数字和中划线，匹配 `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`；建议限制为 64 字符以内。
- 场景及模型 `name` 必填且非空，允许中文。模型 `key` 必须由来源方提供具有语义的名称，例如 `pine-tree`，不能依赖导入器翻译名称；语义合理性由来源方负责，程序只检查格式。
- 模型 `category` 必填，`tags` 可选。实例 `name` 可选，缺省采用模型名称加实例 ID。
- `models[].key` 和 `instances[].id` 各自在声明内唯一；每个 `modelKey` 必须存在，实例变换必填。
- 示例中的模型文件定义局部几何；实例变换作用于文件完整根节点之外，文件内部变换保留。实例旋转固定为 XYZ 角度制；坐标和单位按 `coordinates` 解释。
- `environment`、非空 `cameras` 必填，采用当前原生字段子集。SDK 必须从显式选择的相机生成这些数据，不能自动猜测活动相机。只交换资产时，应使用独立的模型导入入口。
- 首版文件入口只接受一个完整文件定义一个模型；多资产场景通过 SDK 按显式根节点导出独立模型文件。不通过不稳定的节点名称搜索或 UUID 猜测定位。
- SDK 必须移除已记录到实例变换中的根布局变换，避免模型文件和实例重复应用它；不能直接把带世界位置的对象导出后再次叠加相同位置。

## 3. 文件目录与资源完整性

### 3.1 不限制来源目录名称

下面两种结构都可以作为输入来源：

```text
来源 A/                         来源 B/
├─ chair.gltf                  └─ furniture/chair/
├─ chair.bin                      ├─ model.gltf
└─ textures/wood.png              ├─ mesh.bin
                                 └─ images/wood.png
```

前提是模型文件中的引用能够找到对应资源。相对路径以引用文件所在目录为基准；导入时必须保留目录关系，不能把同名贴图全部平铺到一个文件夹。

### 3.2 必须满足的条件

- 提供所有被引用的模型、buffer、图片及环境资源。隐藏资产的依赖也必须包含。
- 建议使用相对路径。机器绝对路径、盘符路径和源服务器根路径必须在导出时重写为包内引用。
- 远程 URL、临时 Blob URL 不构成可移交资源；源 SDK 应读取允许访问的资源字节并打包。无法读取时报告缺失，不能把临时地址直接写入交付包。
- 资源路径必须落在提交的包内，不允许向包外访问。避免只有大小写不同的文件名，保证跨平台可用。
- 解码所需扩展必须在插件支持清单中；使用 Draco、KTX2 等资源前应核对实际插件能力。

缺失贴图、摘要不匹配、路径冲突等问题必须在提交前解决。插件不得以默认材质或红色占位模型替代后宣称导入成功。

## 4. 基础形状拼装的模型

### 4.1 可以导入

例如一张桌子由以下对象组成：

```text
Table（一个完整资产）
├─ TableTop：BoxGeometry
├─ Leg01：CylinderGeometry
├─ Leg02：CylinderGeometry
├─ Leg03：CylinderGeometry
└─ Leg04：CylinderGeometry
```

源应用生成这些几何体后，SDK 读取实际网格、材质、贴图和变换。转换器将它们保存为一个规范模型：

```text
models/table-<唯一标识>/
├─ meta.json
└─ model.glb
```

一个模型可以包含多个网格和材质，不要求把桌面和桌腿合并成一个 Mesh。3D-Layout-Agent 将整张桌子作为一个布局资产处理，模型内部可保留必要层级。

### 4.2 保留与不保留的内容

| 内容 | 第一版目标 |
|---|---|
| 导出时实际生成的几何形状 | 保留 |
| 支持范围内的材质、贴图和各部件相对位置 | 保留 |
| 整体资产在场景中的位置、旋转和尺寸 | 保留 |
| 生成模型的 JavaScript 源码 | 不作为可执行资产保留 |
| “桌腿半径”等参数化建模能力 | 不保证保留；转换后以静态几何为准 |
| 持续动画、物理行为、事件回调 | 不属于首版静态布局导入范围 |

如果需要在导入后独立编辑桌面和桌腿，就必须将它们声明为独立资产。这会改变 Agent 的操作粒度，应按实际业务选择。

## 5. 资产边界与对象树

### 5.1 什么算一个资产

一个资产是可以被编辑器或 Agent 独立移动、旋转、缩放、删除的对象，例如一张桌子、一把椅子、一盏灯。

源项目必须在交付之前确定边界：SDK 接收显式资产根节点及模型/实例标识；文件输入则按声明将完整文件绑定到一个模型。整间房屋若需要分别编辑家具，必须由来源方先拆分或明确标注后通过 SDK 导出。

没有声明时拒绝自动导入，返回 `MISSING_ASSET_DECLARATION`。不默认拆 Mesh，不调用大模型，不自动把未声明场景当成一个资产。来源方可以明确声明整场景为单资产，但必须接受整体编辑粒度。

所有需要保留的可渲染节点必须恰好属于一个资产根；被排除的节点必须由来源方明确列出。未覆盖的节点、重叠根节点都应阻断导出，避免悄悄丢失模型。相机、灯光通过专用配置处理，不当成家具资产。

不允许同时把一个节点及其后代节点声明为两个重叠资产，否则会重复导入。仅凭 `Group`、`Mesh` 类型或节点名字不能可靠判断家具边界。

### 5.2 层级差异的处理

```text
源场景
Scene
─ RoomGroup
  └─ FurnitureGroup
     └─ Table
        ├─ TableTop
        └─ Legs

目标场景
SceneDocument.assets
└─ TableInstance → TableModel
```

布局层祖先节点的位置、旋转和缩放会合并进资产世界变换；资产根内部的部件关系由模型保存。转换前后比较的是物体在世界空间中的形状和位置，不要求对象树完全相同。

若源父组隐藏，则资产的有效可见性也必须考虑父组状态。导出时应冻结一份一致的场景快照，避免遍历过程中动画继续改变节点状态。

## 6. 单位、坐标与变换

目标规范固定为：单位米、右手坐标系、+Y 向上、模型原点位于底面中心；实例旋转存为 XYZ 顺序的欧拉角，单位为度。

源数据不必提前符合目标规范，但必须提供足够的转换信息：

- 对运行时 Three.js 场景，声明一个场景单位对应多少米，并说明向上轴及是否存在额外坐标约定。
- 对有明确格式约定的输入，按格式解析，同时检查节点中的实际变换。
- 未声明单位或必要坐标约定时拒绝自动导入，要求来源方补齐；不能通过物体外形猜测单位。
- 所有变换数值必须有限，不接受 NaN、Infinity 或不可逆的退化变换。

插件调整单位、方向和原点时，必须补偿实例变换，保证世界位置不变。尤其不能只把模型顶点移动到底面中心，却不更新场景中的位置。

父级非均匀缩放与旋转可能产生剪切。当前布局数据只能表达位置、旋转、缩放：遇到剪切或镜像时，转换器必须完成经过验证的几何烘焙，或者明确拒绝。未实现烘焙的版本不能静默忽略这类变换。

## 7. 材质与动态特性要求

下表是首版静态转换的目标范围，具体子集需由实现版本公布。

| 内容 | 准备要求与处理规则 |
|---|---|
| 普通静态 Mesh、基础形状 | 提供有效顶点、索引等几何数据及所需材质 |
| 标准 PBR 材质与图片贴图 | 使用经插件验证的子集；确保 UV、贴图和纹理变换完整 |
| 自定义 ShaderMaterial | 预先转为受支持材质或烘焙；无法等价转换时拒绝或显式接受降级 |
| GPU 顶点位移 | 必须生成对应的静态几何，否则不能保证最终形状一致 |
| 程序化/Canvas 纹理 | 导出前固定为可读取的图片快照，并检查材质语义 |
| 视频纹理 | 只能在支持时固定为指定帧；视频播放行为不保留 |
| 骨骼动画、morph | 指定时间和权重，使用已实现的姿态烘焙；否则拒绝 |
| InstancedMesh | 转换器可展开为独立布局实例，共享规范模型；实例颜色等属性也需验证支持 |
| 点云、线段、自定义渲染对象 | 不默认视作可导出的三角网格；需要专用适配或明确排除 |
| 后处理、物理、交互脚本 | 不属于首版交换范围 |

严格导入模式下，无法表达的内容阻断提交。用户选择静态化或降级时，报告必须列明受影响对象、处理方法和丢失内容；不能笼统标为“无损”。

## 8. 相机、灯光与环境

当前中立场景只提供有限的相机与环境字段，因此“模型一致”不等于“任意 Three.js 应用画面逐像素一致”。

- 纯色背景、支持的 HDRI 可以映射到场景/视图配置，HDRI 必须随包提供。
- 只有能映射到现有相机契约的参数可直接保留；正交投影、相机 roll 等不能静默丢弃。
- 任意灯光阵列、阴影设置和后处理不能自动等价映射到当前固定灯光系统。
- 严格场景导入遇到不支持的显示配置时应拒绝；用户也可明确选择仅导入模型布局，使用目标场景的显示配置。
- 截图比较需要固定相机、灯光、渲染版本和色调映射；几何与资源校验才是模型一致性的主要依据。

## 9. 代码生成场景的 SDK 使用约定

源应用应在模型、图片、异步几何等全部准备好后导出，不应在加载刚开始时提交空场景。SDK 会执行独立资源预检，不能仅凭源页面看起来正常就判断资源可导出。

下面展示预期调用信息，**仅为接口草案，不是已经可以安装调用的 API**：

```ts
// 由源应用完成资源加载、固定动画姿态，并更新世界矩阵后调用。
const result = await layoutExporter.exportScene({
  scene,
  sceneInfo: { id: 'demo-room', name: '示例房间' },
  assets: [
    { root: tableGroup, instanceId: 'table-001', modelKey: 'table',
      modelName: '餐桌', category: 'furniture' },
    { root: chairGroup, instanceId: 'chair-001', modelKey: 'chair',
      modelName: '椅子', category: 'furniture' },
  ],
  excludedRoots: [],
  coordinates: { metersPerUnit: 1, up: '+Y', handedness: 'right' },
  profile: 'layout-static-v1',
  camera: mainCamera, // 来源方显式指定；适配器校验可表达性
  environment: { background: '#1c2128', sunIntensity: 1.6 },
});
// 检查 result.report；无阻断错误后再交付生成的场景包。
```

SDK 必须校验覆盖范围：本例只声明两个资产根，其他可渲染对象必须补充声明或列入 `excludedRoots`，否则报错。预检报告应列出排除内容和有效可见性。生成器使用随机数或时间时，应在导出时固定实际生成结果，确保同一次导出内部一致。同一 `modelKey` 的实例必须具有相同局部模型内容；不同材质或几何应使用不同 key，冲突时不能静默选择其中一个。

## 10. 模型身份与复用模式

插件提供两种业务模式：

| 模式 | 行为 |
|---|---|
| 允许新模型（默认） | 输入规范化后写入全局 `assets/models/`，场景以原生 ref 引用 |
| 仅允许已有模型 | 必须经过内容及模型定义验证匹配现有模型库，未匹配则拒绝或等待显式映射 |

模型名称、文件名、Three.js UUID、尺寸和外观相似度都不能单独证明是同一个模型。来源 ID 只是匹配线索，还要校验内容。

内容哈希一致可以证明对应字节一致；不同编码但外观相同的模型可能哈希不同，因此不能通过哈希不等就断言视觉不同。此类情况需要进一步比对，不自动复用。

用户指定“使用库中另一模型替换”属于替换，不属于保真转换。报告必须说明替换关系和尺寸差异。

## 11. 导入后的交付结果

成功导入后，工程目录应具备以下内容：

```text
3D-Layout/
├─ scenes/
│  ├─ index.json
│  └─ demo-forest/
│     ├─ scene.json
│     ├─ threejs/view.json
│     └─ import-report.json
└─ assets/
   ├─ models/
   │  ├─ manifest.json
   │  └─ demo-forest-pine-tree/
   │     ├─ meta.json
   │     └─ model.glb
   └─ hdri/                   # 有环境依赖时一并写入
```

命名与映射采用确定性规则：默认模型 ID 为 `<scene.id>-<model.key>`，示例 ref 为 `models/demo-forest-pine-tree`；`meta.json.id` 与目录名相同，`name/category/tags` 来自声明，`dimensions` 从实际规范几何测量，`source` 为 `{ "type": "glb", "file": "model.glb" }`。如果项目后续确定另一种语义命名顺序，统一调整命名器即可，不通过大模型生成路径。

同一 ID 已存在且规范定义和元数据一致时复用；同名内容不同默认拒绝，可通过预先配置的 `suffix-hash` 策略追加内容摘要前缀并统一改写 ref。短摘要若碰撞应延长，不覆盖旧模型。场景 ID 已存在时，默认拒绝；同一输入的重复导入可根据完整导入记录判定无变化，不重复创建。实例 ID 保持声明值。

落盘遵循“预检全部通过 → 暂存模型和场景 → 校验引用 → 发布模型及场景 → 更新索引 → 打开场景”。多目录发布需要写锁和恢复日志；失败回滚本次新增内容，不删除复用的既有模型。现有保存接口不能承担该流程，必须新增受控本地导入服务或命令行工具。仅静态网页不能直接写入上述工程路径，可生成相同目录结构的待安装文件集。

写入原生 `SceneDocument`、`ModelMeta` 和 `ViewBinding` 格式；导入声明只作为转换输入，不能直接替代 `scene.json`。外部 Three.js 源码不作为新的页面在 3D-Layout 内执行，模型由现有通用渲染器打开。必要来源文件可作为附件归档，不影响原生加载入口。

规范模型是渲染、Agent 尺寸判断和再次导出的共同依据。同一模型的多个实例共享模型文件，各自保留独立 ID 和变换。需要导出场景时，再收集其引用的全局模型一并交付。

成功标准包括：全部引用可解析；支持范围内的世界几何、材质和尺寸符合容差；有效可见性被保留；无未处理的阻断问题；离线打开时不请求外部模型和贴图。应用运行时代码和解码器仍由宿主部署负责。

## 12. 提交前检查与常见问题

提交前确认：

- 已选择支持的输入方式，并提供完整资源。
- 已声明单位及必要坐标约定。
- 已提供完整导入声明、语义 key/name/category，资产根没有祖先/后代重叠，待保留节点无遗漏。
- 动态生成已完成；动画、程序纹理等已明确静态化策略。
- 已查看不支持内容、排除对象和降级报告。
- 已选择允许新模型或严格复用模式。

| 问题 | 处理方法 |
|---|---|
| 模型有形状但没有贴图 | 补齐图片和正确引用；检查跨域资源是否可读取 |
| 整个房间只能一起移动 | 重新选择家具级资产根节点 |
| 桌腿被当成独立家具 | 把桌子 Group 作为资产根，取消对子节点的独立选择 |
| 导入后尺寸大 100 倍 | 检查源单位声明，重新转换；避免盲目叠加实例缩放 |
| 旋转父组下的模型变形 | 检查剪切和镜像，使用受支持烘焙流程或调整源变换 |
| 同名模型被判为不同模型 | 比较内容和材质；名称相同不保证内容相同 |
| JS 项目没有模型文件 | 在源应用中通过 SDK 导出生成后的场景 |
| 严格模式无法导入自定义着色器 | 先烘焙为受支持表示，或明确缩小导入范围 |

导入失败应定位到文件或节点并说明原因。失败、取消或预检未通过时，不改变当前场景及其撤销/重做历史。
