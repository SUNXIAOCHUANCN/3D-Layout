# 场景与编辑历史持久化技术设计

## 目标与范围

当前实现解决本地单用户编辑的可靠保存：刷新、切换场景或服务重启后，场景、撤销栈和重做栈一致恢复；离线提交可在同一标签页刷新后重试；多标签页修改不会静默相互覆盖。

使用原有 `SceneDocument` 和 `core/edit.ts` 事务边界。没有增加 ORM、消息队列或外部数据库依赖。多人实时协作、账号权限、自动历史清理、模型资源 CRUD 和版本管理 UI 不在本次实现范围。模型元数据仍使用文件目录，数据库维护版本资源引用。

## 模块

| 文件 | 职责 |
|---|---|
| `server/workspaces.mjs` | SQLite 迁移、工作区校验、事务提交、版本恢复、文件投影 |
| `server/http.mjs` | HTTP 路由、请求限额、来源检查、错误映射 |
| `server/start.mjs` | 构建后的独立 API 与静态文件服务 |
| `server/backup.mjs` | SQLite 在线备份 |
| `src/core/workspaceTypes.ts` | 前端工作区类型 |
| `src/core/persistence.ts` | IndexedDB 队列、串行提交、状态与恢复 |
| `src/core/edit.ts` | 编辑事务、历史恢复、提交边界通知 |
| `src/core/store.ts` | 场景切换、工作区初始化与恢复顺序 |
| `src/ui/TopBar.tsx` | 保存状态、重试、本地副本导出、冲突后重新加载 |

前端使用 TypeScript；后端为原生 ESM JavaScript，并为 Vite 接口提供声明文件，以便 Node 直接运行，无需额外编译步骤。

## 持久化状态

```ts
interface Workspace {
  document: SceneDocument
  journal: HistoryUnit[]
  redoStack: HistoryUnit[]
  txCounter: number
}
```

`revision` 是服务端的单调递增提交编号，独立于旧文档中的 `meta.version`。历史中的数字 `txId` 属于单个场景工作区，恢复时还原计数器，避免刷新后的事务 ID 重复。提交请求使用 UUID `requestId` 做幂等标识。

相机操作、选择和其他观察状态继续不进入编辑历史；源文档中的相机与环境数据随工作区保存。

## 数据库

使用 SQLite WAL、外键、5 秒忙等待和 FULL 同步。结构迁移通过 `user_version` 管理；初始建表在一个数据库事务内完成。

| 表 | 主键与内容 |
|---|---|
| `scenes` | `id`；当前 revision、workspace JSON、更新时间、文件投影标志 |
| `revisions` | `(scene_id, revision)`；request ID、请求摘要、标签、完整工作区、时间；同场景 request ID 唯一 |
| `resource_refs` | `(scene_id, revision, ref)`；当前与历史资产引用，以及当前环境 HDRI 引用 |

已有场景按需导入；第一次读取创建 revision 0 的当前状态，后续提交从 1 开始。初始版本 0 不写入 `revisions`，历史恢复接口接受已提交的版本。

每次提交保存完整工作区，避免先引入复杂事件重放。代价是长时间编辑时数据库增长较快；本版保留全部版本，不做自动裁剪。后续可在保持 API 不变的前提下改为周期快照和增量日志。请求限额 32 MiB；单工作区最多 20000 个资产、100000 条当前可撤销/重做操作，超过限制明确报错。

## 提交流程

```text
编辑事务完成
    → 压缩同资产连续变化
    → 冻结工作区副本，生成 requestId 和 baseRevision
    → IndexedDB 持久化
    → 串行 POST
    → 校验工作区
    → BEGIN IMMEDIATE
        幂等查询
        比较当前 revision
        更新当前状态
        插入版本和资源引用
      COMMIT
    → 更新 scene.json 文件投影
    → 客户端收到确认
    → 删除对应本地队列项
```

同一事务中同一资产只保留第一次 `before` 和最终 `after`，无变化的条目删除；如果最终事务为空，恢复此前 redo 栈。事务失败回滚也恢复原 redo 栈。事务尚未结束时不持久化中间预览；撤销重做和场景切换不应穿插进入未完成事务。

后端检查资产 ID 唯一性、有限数值与正缩放、历史命令及事务 ID。再从当前文档逆向撤销 journal、按栈顺序重做 redoStack，逐步校验操作所需的当前资产状态，拒绝文档与历史不匹配的请求。

这是一种一致性校验，不是授权系统：本地客户端可以提交合法的新工作区。本次未实现远程用户权限。

## 幂等和冲突

请求摘要包含 `baseRevision` 和工作区内容。相同 request ID 的相同内容返回原 revision，即使客户端因响应丢失仍持有旧 baseRevision。相同 ID 换内容则拒绝。新请求仅在当前 revision 等于 baseRevision 时提交。

客户端按本地队列预留连续 baseRevision，不能将冲突后的旧请求简单改成新版本重发，否则会覆盖其他标签页修改。冲突保留本地队列和当前画面，供用户导出；明确放弃后才清除当前标签页队列并重新加载。

## 刷新和离线恢复

进入场景先完成上一场景待提交任务，再读取服务端工作区和当前标签页的 IndexedDB 队列。如有待提交记录，以最后一条本地工作区恢复画面，并按原 request ID 重试。

恢复顺序是先写场景文档、发出 `scene:changed` 清理旧会话、再恢复新场景历史。加载期间拒绝编辑，避免新文档与旧历史交叉。工作区提交与场景文档类型之间只使用类型导入，实际副作用留在编辑和 IO 边界。

本地写入和网络发送分别串行：网络请求失败时，后来产生的编辑仍会尝试落入 IndexedDB，不能被失败的网络 Promise 阻断。本地写入失败保留暂存副本，并显示错误。刷新前采用 `beforeunload` 提醒；它不能替代数据库或 IndexedDB 的成功确认。

限制：只有 IndexedDB 写入完成的待提交项保证能跨刷新恢复；页面被强制终止前尚未完成本地写入的内容无法保证保存。队列使用 sessionStorage 中的标签页身份，主要覆盖同一标签页刷新；关闭标签页、清理站点数据、切换浏览器配置文件等情况不保证自动恢复。

## 文件兼容和导入导出

数据库是已提交工作区的持久化依据。提交后将当前文档写入临时文件，再重命名为 `scenes/<id>/scene.json`。数据库与文件不能组成同一个 SQLite 事务，因此 `projected` 标记记录是否已同步；文件失败时不撤销已提交数据，下次读取或提交会重试。

文件投影用于兼容现有导出插件。文件同步错误尚未修复时，插件导出可能读到旧文件，应先处理顶栏提示。不要同时运行多个后端写进程或在数据库接管后手改场景文件。

导入插件仍按原有文件事务创建新场景和模型。场景列表通过后端扫描目录发现新场景，再初始化工作区；同 ID 重导入仍使用插件的冲突策略。模型库加载继续使用 `assets/model-catalog.json`。没有改写或迁移现有大模型文件。

## API 与运行

开发及 preview 由 Vite 挂载共享 API；生产本地模式由 `server/start.mjs` 提供页面与共享 API。旧的直接覆盖场景保存接口已移除，显式保存等待工作区队列完成，不再将服务器保存失败伪装成文件下载成功。

写请求要求自定义标识和同来源 Origin。静态服务对路径做根目录边界检查，数据库 ID 限定为字母、数字、下划线、短横线；SQL 使用参数绑定。独立服务只监听 `127.0.0.1`。原有 Agent / CoAgent 调用日志接口统一迁移到共享 API，开发和独立运行使用同一实现。

完整运行、接口示例和备份恢复步骤见 [后端 README](../server/README.md)。

## 验证

- 后端测试：服务重启、场景与 redo 栈恢复、文件同步、幂等、冲突、非法历史拒绝、版本恢复、分页及 HTTP 校验。
- 无界面 Edge 测试：真实前端模块与 IndexedDB，覆盖 100 帧拖动压缩、刷新、撤销重做跨刷新、切换场景恢复、离线连续编辑、响应丢失重试及冲突恢复。
- CoAgent 回归：人工与 AI 共用编辑入口，失败事务不会破坏已有 redo 分支。
- 构建检查：TypeScript 和 Vite 生产构建。

测试均使用临时数据；不通过修改真实场景验证数据库行为。
